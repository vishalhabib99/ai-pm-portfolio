# Case Study: Turning an Unsolicited Collaboration Request into a Shipped, Merged Fix in Someone Else's Repo

**Date:** 2026-09-08 to 2026-09-13

## What shipped

[`agent-inspect`](https://github.com/rajudandigam/agent-inspect) — a TypeScript agent-trajectory/evidence-debugging tool maintained by Raju Dandigam (519★/98 forks, actively published on npm) — now ships `--preset behavioral-session` (v6.26.0+), a check mode that keeps a graceful MCP tool rejection (`isError: true`) as a raw execution-status error while scoring the *expected-behavior* verdict on a separate axis, so a healthy crash-resilience session no longer reads as an almost-total failure. The fix was verified against a real 114-call [`mcp-fuzz`](https://github.com/vishalhabib99/mcp-fuzz) session I supplied, and that sanitized session is now a maintainer-reviewed, attributed fixture merged into AgentInspect's own repo ([PR #403](https://github.com/rajudandigam/agent-inspect/pull/403)), documented in a permanent recipe (`examples/recipes/mcp-behavioral-session/`).

## Key decisions & tradeoffs

- **Ran the experiment instead of replying with opinions.** Raju's initial email (2026-09-08) asked for candid feedback on where AgentInspect's evidence model was useful or incomplete. Rather than answering from a docs read, I wrote a capture script reusing mcp-fuzz's own input generators, fed a real 114-call session against [`codebase-memory-mcp`](https://github.com/DeusData/codebase-memory-mcp) (42.7k★) into AgentInspect's ingest path, and reported what actually happened — including a genuine gap: `isError: true` (a *good*, graceful-rejection outcome) collapsed straight into AgentInspect's generic `status:error`/"failed" vocabulary, so 104 of 114 calls read as failures despite a clean 100%/A crash-resilience result.
- **Kept execution status and behavioral verdict conceptually separate rather than proposing to rewrite history.** Raju's 2026-09-09 reply set the real constraint: `isError: true` must keep meaning "the tool invocation errored" — coercing an expected rejection to `ok` would erase real execution evidence. The actual gap was that nothing scored *whether the rejection was the correct outcome* as a separate fact. I built a working demonstration against AgentInspect's own `outcome_observed` schema (v4.4.0+) proving that split already existed in the SDK, just not wired into a documented check — and filed it as [agent-inspect#362](https://github.com/rajudandigam/agent-inspect/issues/362) with exact repro commands rather than a description of the idea.
- **Granted attribution rights only once the reproduction was public and verified**, not on the first ask — Raju requested permission to adapt the sanitized session into a repository fixture on 2026-09-10, after his own review had already validated the approach; permission was given the same day once the specific reuse (a fixture with attribution, no private data) was clear.

## What broke / what didn't work

The first command I shipped in issue #362 was wrong in a way Raju caught, not me: `--fail-on-observation failed` with no explicit `--rule` *adds* `outcome.status` findings on top of the default `run.status` check — it doesn't replace it. My original repro therefore still showed a spurious blanket failure alongside the real per-call findings. Raju's 2026-09-10 reply supplied the corrected invocation (`--rule outcome.status --fail-on-observation failed`) and explained precisely why the omission mattered — the same "verify the actual boundary, don't guess" standard this portfolio holds itself to, applied by someone else to my own output. I didn't defend the original command; the corrected version is what shipped in the merged recipe.

## Outcome

**Merged 2026-09-13** via [agent-inspect#403](https://github.com/rajudandigam/agent-inspect/pull/403) — a real feature (`--preset behavioral-session`, v6.26.0+) shipped and cited by name, not just a maintainer reply or an acknowledged bug. Reran the exact documented commands the same day against current `main` (v6.29.1, published hours earlier) to check for drift rather than taking the merge announcement at face value: the merged fixture is byte-identical to the original conversion, the default `check` reproduces the same single `run.status` collapse, and `--preset behavioral-session` reproduces the documented contrast exactly (`run.requireCompleted` passes, all 21 findings come from `outcome.status`) — no regression through review or merge. Reported the reverification back to Raju the same day, closing the loop with the actual maintainer of record rather than treating the merge notification as the finish line.

This is the first collaboration in the portfolio's history where an external maintainer built and shipped something citing my work by name — a materially different, stronger signal than the other outreach issues in this portfolio, which have topped out at "maintainer acknowledged and fixed their own bug." The difference: this one required getting the *design* right together, being corrected on a real mistake, and proving the fix held up under independent re-test — not just filing an accurate report.
